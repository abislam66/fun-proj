# Deployment

> **OpenOwls SDD** — Read by engineers and DevOps-minded team members.
> Defines how the application is built, configured, and deployed across environments.
> Claude Code uses this file to understand deployment targets and avoid environment-specific mistakes.

---

## Environments

| Environment | Purpose | Notes |
|-------------|---------|-------|
| Local | Development on your own machine | `next dev` against the **tueats-dev** Supabase project (a free-org project — no Docker required). |
| Staging | Pre-production testing | **Vercel preview deployments** — one per PR, automatic. Previews point at **tueats-dev** (same DB as local), so a preview never touches production data. |
| Production | Live for real users | Vercel production deployment from `main`, pointed at **tueats-prod**. |

> **Golden rule:** changes flow **local → staging → production**. Never test a risky migration
> or code change directly against production.

Concretely for TuEats: every migration is applied to **tueats-dev first**, exercised locally and on a preview deploy, and only then applied to **tueats-prod**.

## Hosting Platforms

| Component | Platform | Tier | Notes |
|-----------|----------|------|-------|
| Next.js app | Vercel | Hobby (free) | Git-integrated CI/CD; preview per PR; instant rollback. |
| Postgres + Auth (prod) | Supabase | **Pro — existing $25/mo plan** | `tueats-prod` lives in the paid org: daily backups (7-day retention), no idle-pausing. Billing nuance: Pro orgs bill ~$10/mo compute per active project against a $10/mo included credit — marginal cost is $0 only while no other project in that org consumes the credit. |
| Postgres + Auth (dev) | Supabase | Free org | `tueats-dev` lives in a **separate free org** — $0 forever. Free projects pause after ~1 week idle; a one-click dashboard "restore" fixes it and only ever affects dev. |
| Auth verification email | Resend via Supabase SMTP | Free | Configured inside Supabase (Auth → SMTP) per project; credentials never in app env. |
| Map tiles | OpenFreeMap | Free public instance | No account, no key. Swappable via `NEXT_PUBLIC_MAP_STYLE_URL` if it ever degrades. |
| Domain | `tueats.vercel.app` (default) | Free | A custom domain is the project's only *potential new* spend — optional, decision deferred. |

Supabase **branching** (a Pro feature) is deliberately not used: preview branches bill compute per hour and their auto-migration flow assumes Supabase CLI migrations rather than Drizzle. The two-project layout covers the same need with zero moving parts.

## Packaging

No containers, no servers. The Next.js build on Vercel produces static/ISR pages plus serverless functions for dynamic routes and server actions — Vercel's Git integration handles build and deploy on every push.

Two things deliberately **outside** the build:

- **Database migrations** — plain SQL files in `drizzle/`, generated by `drizzle-kit generate` and applied explicitly with `pnpm db:migrate` (using `DIRECT_DATABASE_URL`). Migrations are **never** run automatically during a Vercel build; a failed half-migration inside a build is the worst failure mode this project could have.
- **Seeding** — `pnpm seed:kml` is a local, idempotent script run by hand against whichever environment's env file is loaded. It creates draft venues only, so even a mistaken prod run publishes nothing.

## Environment Variables

| Variable | Required | Description |
|----------|----------|-------------|
| `DATABASE_URL` | Yes | **Pooled** Supabase connection string (Supavisor, transaction mode, port 6543) — app runtime. |
| `DIRECT_DATABASE_URL` | Yes (migrations only) | Direct connection (port 5432) for `drizzle-kit`. Not needed by the deployed app — set locally, optional in Vercel. |
| `NEXT_PUBLIC_SUPABASE_URL` | Yes | Supabase project URL — differs between dev and prod projects. |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Yes | Auth-only key; safe to expose because RLS denies all data access. |
| `NEXT_PUBLIC_SITE_URL` | Yes | Canonical URL per environment (localhost / preview URL / production) — drives auth redirects and OG tags. |
| `NEXT_PUBLIC_MAP_STYLE_URL` | Yes | OpenFreeMap style URL — the one-value tile-provider swap. |
| `IP_HASH_SALT` | Yes | Salt for anonymous-report IP hashing. Different value per environment. |

> ⚠️ Never commit `.env` files or real secret values. Keep a `.env.example` with dummy values checked in.

In Vercel, Preview and Production environments hold **different values** for the Supabase variables (dev project vs prod project) — this is what makes previews safe by construction.

## Local Development Setup

### Prerequisites
- Node.js 22 LTS
- pnpm 10 (`corepack enable`)
- A Supabase account with access to the **tueats-dev** project (free)
- Git

### Steps

```bash
# 1. Clone the repository
git clone [repo-url]
cd tueats

# 2. Install dependencies
pnpm install

# 3. Configure environment
cp .env.example .env.local
#    Fill in values from the tueats-dev Supabase project
#    (Settings → API for URL/anon key; Settings → Database for connection strings)

# 4. Apply migrations to the dev database
pnpm db:migrate

# 5. (First time / empty DB) Seed draft venues from the Temple KML export
pnpm seed:kml

# 6. Run
pnpm dev          # → http://localhost:3000
```

Script names are conventions: `db:generate` (create a migration from schema changes), `db:migrate` (apply), `seed:kml` (idempotent import), `test`, `test:e2e`.

## Deployment Process

### Staging (automatic)
1. Open a PR — Vercel builds a preview deployment against **tueats-dev**.
2. If the PR contains a migration: apply it to tueats-dev (`pnpm db:migrate` with dev env) *before* review, so the preview runs against the migrated schema.
3. CI (typecheck, lint, format, tests, build) + Playwright smoke against the preview URL must pass.

### Production
1. Merge to `main` only with CI green and the preview verified by hand (it's a solo project — look at the thing).
2. If the release contains a migration: apply it to **tueats-prod first**, then merge. Order is always **migrate → deploy**, which works because migrations must be backward-compatible with the previously deployed code (additive changes; destructive cleanup ships one release later).
3. Vercel deploys `main` to production automatically.
4. Smoke-check production: home map loads, one venue page renders, admin sign-in works.

### Rollback
- **Code:** Vercel → instant rollback to the previous deployment (one click, no rebuild).
- **Database:** never rolled back — the backward-compatibility rule means old code runs safely against the new schema, so code rollback alone is always sufficient. (A migration bad enough to need reversal gets a new forward migration.)

## CI/CD Pipeline

**On every pull request:**
- GitHub Actions: `pnpm typecheck` → `eslint` → `prettier --check` → `vitest run` → `next build`
- Vercel: preview deployment (parallel to CI)
- Playwright smoke suite against the preview URL
- All checks are required — a red check blocks merge (branch protection on `main`)

**On merge to `main`:**
- Same checks re-run; Vercel deploys to production on success
- No scheduled jobs exist in this project (nothing to cron)

Note: Vercel deploys on push regardless of GitHub checks by default — turn on **"Require checks to pass before deploying"** (Vercel Git settings) so production waits for CI.

## Common Deployment Issues

| Issue | Likely Cause | Fix |
|-------|-------------|-----|
| Build works locally, fails on Vercel | Env var missing in Vercel project settings | Add it to the right environment (Preview vs Production have separate values here — check both). |
| Random `too many connections` / timeouts in production | App is using the **direct** connection string at runtime | `DATABASE_URL` must be the pooled Supavisor string (port 6543, transaction mode). Direct (5432) is for migrations only. |
| OTP emails link to the wrong host, or auth loops after login | `NEXT_PUBLIC_SITE_URL` wrong for that environment, or the URL missing from Supabase Auth's redirect allowlist | Set the env var per environment and add localhost + preview wildcard + production URLs to Supabase Auth URL configuration (per project). |
| Verification emails never arrive | Supabase's built-in sender (a few emails/hour) still active | Confirm Resend SMTP is configured in that Supabase project — dev and prod are configured **separately**. |
| Admin edits don't show on the site | A write path missing its `revalidateTag` call | Every mutation invalidates the tags it affects (`venues`, `venue:{slug}`) — fix the action, don't add a TTL. |
| Map is blank in production but fine locally | `NEXT_PUBLIC_MAP_STYLE_URL` unset in Vercel (`NEXT_PUBLIC_*` vars are baked at build time) | Set it and redeploy — a runtime env change is not enough for public vars. |
| Everything broke after a "quick" prod migration | Migrate-before-deploy done with a non-backward-compatible change | Re-read the rule: additive first, destructive one release later. Ship a forward-fix migration. |
| Dev database suddenly unreachable after a quiet week | Free-org auto-pause on inactivity (dev only) | Restore the project from the Supabase dashboard (takes a minute); prod is on the Pro org and never pauses. |

## Secrets Management

- All secrets live in the platform's environment settings — never in code or the repo.
- Each environment uses separate keys/secrets.
- Rotate any secret immediately if it is accidentally committed.
- The Supabase **service-role key** is used nowhere — not in Vercel, not in CI, not locally (see `auth-security.md`).
- Resend credentials live inside each Supabase project's SMTP settings, not in this app's environment.
- The only secrets this app actually holds: two connection strings and `IP_HASH_SALT`. Small surface, keep it that way.
